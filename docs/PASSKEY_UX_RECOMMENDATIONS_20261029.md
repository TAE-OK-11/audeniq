# Passkey UX technical recommendations — 2026-10-29

Research only. Ranking reflects expected benefit for this backend, implementation effort, and compatibility. No UX feature below is implemented in this round; no screen, wording, or visual design is prescribed. Browser-managed biometric/PIN and credential-manager policy remain authoritative: “no extra input” cannot mean bypassing user verification.

| Rank | Recommendation | Expected effect | Difficulty | Prerequisites and backend implications |
| --- | --- | --- | --- | --- |
| 1 | Conditional authentication / autofill | Reuse an existing discoverable passkey without requiring an email-first ceremony. | Low–medium | Feature-detect conditional mediation; use existing account-neutral options and optional email login. Coordinate cancellation and challenge refresh with the 300-second server expiry. Keep password fallback and all assertion verification. |
| 2 | Continue discoverable credentials and stable opaque user handles | Supports account selection by the authenticator and avoids requiring email input when the credential already identifies the user. | Low | Existing registration already requires resident credentials and uses user UUID bytes; login already accepts absent email and validates supplied userHandle. Preserve these contracts; measure adoption without logging identifiers. This is reuse of existing backend behavior, not a new endpoint proposal. |
| 3 | Credential synchronization using Signal API | Reduce stale credentials and account-detail mismatches in authenticators, without asking users to re-enter details. | Medium–high | Feature-detect each method. A future authenticated owner-only API would return the complete credential-ID snapshot and user handle; current list deliberately does not expose IDs. Invoke only after committed changes. Never send another account's IDs or a partial/paginated snapshot. Gate rollout on multi-account platform regression tests. |
| 4 | Preserve required user verification; avoid redundant application reauthentication | Keeps passkey sessions eligible for MFA and sensitive-operation proofs while reducing repeated password entry where a fresh proof already exists. | Medium | Keep UP and UV required and the five-minute, one-use proof. Audit future enrollment authorization separately. Changing to `preferred` would conflict with current session MFA assumptions and is not recommended. |
| 5 | Defer conditional creation pending a separate security-policy decision | Eligible password-manager users could upgrade without another application password prompt. | High; blocked by current invariants | Conditional creation can return UP=false and UV=false, which this backend must reject. Do not enable it against current registration or relax either check in this round. Future work would require explicit authorization for a distinct ceremony policy plus recent, fully verified login and short-lived, session-bound, single-use enrollment authorization. Feature-detect `conditionalCreate`; provider eligibility/settings still apply. |
| 6 | Defer PRF and largeBlob until a concrete encrypted-data use case exists | Little direct enrollment benefit; may support future client-side secret unlocking or credential-associated data. | High | Optional extensions require capability and output checks, recovery/key-lifecycle design, and cross-provider testing. Never send PRF output to logs or use largeBlob as the authoritative account database. They do not increase server-side signature strength or eliminate browser consent requirements. |

Conditional autofill waits for credential selection and can coexist with password fallback; it does not silently authenticate the user. Reuse current discoverable options rather than adding account-enumerating credential hints. [Google implementation guidance](https://web.dev/articles/passkey-form-autofill).

Conditional creation is a distinct post-login upgrade mechanism. Silent success depends on credential-manager policy and recent password sign-in, not a guarantee for every user. [Apple platform guidance](https://developer.apple.com/videos/play/wwdc2024/10125/). Crucially, automatic creation may return both UP and UV unset; current registration requires both. It is therefore a deferred research option, not a compatible switch for this backend. Any future exception needs a separately reviewed ceremony and must never weaken ordinary registration or login verification. [Chrome conditional-create caveats](https://developer.chrome.com/docs/identity/webauthn-conditional-create).

For synchronization, prefer `signalAllAcceptedCredentials` only in an authenticated account context, `signalCurrentUserDetails` after verified account changes, and carefully scoped `signalUnknownCredential` for a rejected unknown credential. Do not infer that every failed assertion means the credential was deleted. Capability detection is necessary but insufficient for safety: test provider behavior before enabling reconciliation. [Chrome passkey management guidance](https://developer.chrome.com/docs/modern-web-guidance/guides/security/passkey-management). A reported WebKit multi-account deletion regression makes platform validation a rollout prerequisite, not evidence that every current platform is affected. [WebKit issue 322267](https://bugs.webkit.org/show_bug.cgi?id=322267).

The recommendation to retain required verification follows this repository's MFA contract. PRF provides credential-associated pseudorandom output; largeBlob provides optional opaque storage, with writes in authentication ceremonies. Neither is needed for ordinary passkey login. [WebAuthn Level 3, verification and extensions](https://www.w3.org/TR/webauthn-3/).

Future validation should cover two accounts on one RP, provider/browser cancellation, expired challenges, duplicate upgrades, credential deletion followed by synchronization, and unsupported extensions. Measure success/cancellation/expiry using bounded reason codes, never credential IDs, AAGUIDs, tokens, or assertion payloads. Frontend implementation and any product design decisions belong to a separate authorized task.
