# 개인정보 암호화

계좌번호와 같은 방식으로, DB에 저장하는 개인정보를 애플리케이션에서 AES-256-GCM으로 봉인한다. 키는 계좌번호와 같은 키링(`crates/core/src/payout_keys.rs`)이다. KMS 모드(`PAYOUT_KMS_ENABLED=true`)에서는 이 키링이 클라우드 KMS로 감싸져 있다가 host tmpfs에만 풀린다([KMS 키 준비와 회전](BACKEND_SECURITY_2026-10-03.md#kms-키-준비와-회전)). 필드마다 KMS를 호출하지 않는 봉투 암호화다. DB, 백업, DB 관리자 권한만으로는 값을 읽을 수 없다.

## 봉인하는 값

| 표 | 값 | 찾기 |
|---|---|---|
| `identity.users` | 로그인 이메일 | 블라인드 인덱스 `email_bidx` |
| `portal.account_identities` | 본인인증 실명, 생년월일 | 없음 |
| `portal.payout_accounts` | 예금주 (계좌번호는 이미 봉인) | 없음 |
| `portal.payout_requests`, `finance.payout_orders` | 신청 시점 예금주 (`holder_cipher`), 계좌번호 사본 | 없음 |
| `portal.artist_profiles` | 연락 이메일 | 없음 |
| `work.relationship_contacts` | 담당자 이름, 이메일, 전화 | 없음 |
| `portal.tax_residencies` | 납세자번호 (TIN 전용 AAD로 옮김) | 없음 |

- **AAD:** 열 이름과 행 주체 id(사용자, 조직 또는 담당자 id)를 묶는다. 암호문을 다른 열이나 다른 사람 행으로 옮기면 복호화가 실패한다.
- **키 버전:** 암호문 머리에 있다. 옛 버전은 키링에 남아 있는 동안 계속 읽힌다.
- **블라인드 인덱스:** HMAC-SHA256이다. 키는 키링의 각 버전에서 따로 유도하며, AES 키를 그대로 쓰지 않는다.
  - 로그인과 가입 중복 검사는 남아 있는 모든 버전의 인덱스와 비교한다.
  - 가입은 주소별 advisory lock으로 직렬화한다.
- **알림:** 계좌 등록 알림 문구에는 은행과 끝자리만 남기고 예금주는 넣지 않는다. 기존 알림에 있던 예금주는 0102가 지운다.
- **요청 제한:** 버킷(`identity.auth_limits`) 이름에는 이메일, 전화번호, IP가 들어간다. 이 버킷 해시를 서비스 비밀 HMAC으로 바꿨다. 배포 직후 한 번 제한 창이 초기화된다.

SQL에서 JSON을 만드는 화면은 값 대신 `{"$pii": …}` 표식을 넣는다. `pii::reveal`이 응답 직전에 이 표식을 복호화한다. 빠뜨린 표식이 있어도 응답에는 암호문만 나간다.

## 운영 절차

1. **키:** production API는 키 없이는 시작하지 않는다(`PII_KEYRING_REQUIRED`). `deploy.sh`도 배포 전에 키를 확인한다. KMS 모드를 권장한다. KMS를 끈 상태라면 `PAYOUT_ACCOUNT_KEY` 또는 `PAYOUT_KEYRING_FILE`이 필요하다. 이미 계좌를 저장한 운영이라면 그 키를 그대로 쓴다.
2. **배포:** 마이그레이션 0102를 배포한다. 이때부터 새로 쓰는 값은 모두 암호문이다. 기존 평문 행은 그대로 읽힌다.
3. **기존 행 봉인:** owner DB 연결과 키(KMS 모드는 tmpfs 키링)를 준비하고 다음을 반복한다.

   ```bash
   audeniq-admin --operator NAME privacy encrypt-pii
   ```

   - 표마다 100행씩 봉인하고, 같은 일을 하는 다른 실행이 잡은 행은 건너뛴다(`SKIP LOCKED`).
   - `total: 0`이 될 때까지 실행한다. 값은 출력하지 않고 표별 개수만 감사 로그에 남긴다.
4. **키 회전:** 새 버전을 active로 만든 뒤 `privacy reencrypt-accounts`와 `privacy encrypt-pii`를 각각 0이 될 때까지 실행한다.
   - `encrypt-pii`는 옛 버전 암호문과 블라인드 인덱스를 새 버전으로 바꾼다.
   - 계좌번호 사본(지급 신청, 지급 지시)도 함께 바꾼다.
   - 옛 키 버전은 백업이 만료되기 전에는 지우지 않는다.
5. **평문 열 삭제:** 모든 운영 DB에서 `encrypt-pii`가 0이 되면 평문 열(`email`, `real_name` 등)을 지우는 후속 마이그레이션을 배포한다. 그 전까지는 평문과 암호문을 모두 읽는다. 한 행의 한 값은 CHECK로 둘 중 한 형태만 허용한다.

## 바뀐 동작

- **문서 작성자 검색:** 운영 화면의 문서 검색은 작성자를 이메일 앞부분이 아니라 전체 이메일로만 찾는다. 이메일이 봉인돼 있어 부분 검색을 할 수 없다.
- **목록 정렬:** 스태프·담당자 목록의 이메일 정렬은 DB가 아닌 서버에서 한다.
- **운영 CLI:** 스태프 계정 관리(`audeniq-admin staff`)와 지급 명령은 이메일과 예금주를 읽으므로, API와 같은 키를 환경에 지정해야 한다.
- **키가 없을 때:** 개발 환경에서 키를 지정하지 않으면 가입, 본인인증, 연락처 저장이 거절된다. 테스트는 `PAYOUT_ACCOUNT_KEY`를 지정한다.

## 아직 봉인하지 않은 값

- **전자서명 기록:** 서명 이미지, 서명자 이름, 서명 요청의 본인인증 정보, 계약서 본문과 전자문서 기록이 해당한다. 인증서 해시와 해시 체인이 평문에 걸려 있고, 서명 이미지 안전성 검사도 원본 해시로 찾는다. 그래서 검증 방식을 함께 바꾸는 별도 작업으로 진행한다.
- **변경할 수 없는 감사 기록:** `privacy.staff_access_logs`의 스태프 IP와 `portal.signing_events`의 브라우저 정보는 추가만 되는 기록이라 기존 행을 바꿀 수 없다.
- **공개 표시 값:** 활동명, 조직 이름 같은 공개 표시 값과 문의 본문 같은 자유 입력 텍스트는 봉인하지 않는다.
