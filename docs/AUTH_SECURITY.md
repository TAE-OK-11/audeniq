# 인증·비밀번호 보안과 법 기준

기준은 다음 세 가지다.

- **한국 (적용 의무):** 「개인정보 보호법」 제29조와 「개인정보의 안전성 확보조치 기준」(개인정보보호위원회 고시)
- **미국 (보안 강화용 참고):** NIST SP 800-63B, FTC Safeguards Rule
- **EU (보안 강화용 참고):** GDPR 제32조

원칙은 세 가지다.

- 서버가 원래 값을 다시 볼 필요가 없으면 **단방향**(해시)으로 저장한다.
- 다시 써야 하는 값(지급 계좌, 표시할 이름, TOTP 비밀)만 **양방향 암호화**한다([개인정보 암호화](PII_ENCRYPTION.md)).
- 서버 부하를 고려해, 무거운 계산은 비밀번호 하나에만 쓴다.

## 값별 저장 방식

| 값 | 방식 | 이유·부하 |
|---|---|---|
| 비밀번호 | **단방향**: Argon2id, 19 MiB, 2회, 1레인, 무작위 솔트 (`auth.rs`) | 고시 제7조(일방향 암호화)와 NIST를 충족하며, OWASP·RFC 9106 저메모리 권장값이다. 1회 약 20 ms이고 동시 실행은 `password_slots`(2)로 제한한다. 파라미터를 코드에 고정해 라이브러리 기본값이 바뀌어도 그대로다. |
| 세션 토큰, CSRF 토큰, 재설정 토큰 | **단방향**: SHA-256 | 256비트 무작위 값이라 느린 해시가 필요 없다. 요청마다 1회, 수 μs다. |
| SMS 인증 코드 | **단방향**: 서비스 비밀과 함께 해시하고, 횟수와 유효시간을 제한 | |
| 연계정보(CI), 휴대폰 번호, 서명 IP | **단방향**: 서비스 비밀을 넣은 SHA-256 | 같은 사람인지 비교만 한다. |
| 요청 제한 버킷 (이메일·전화·IP 포함) | **단방향**: HMAC-SHA256 | 키 없는 해시는 휴대폰 번호처럼 범위가 좁은 값을 되찾을 수 있다. |
| 로그인 이메일 | **양방향 + 블라인드 인덱스** (HMAC) | 화면에 보여 줘야 하고, 로그인할 때 찾아야 한다. |
| 계좌번호, 납세자번호, 실명, 생년월일, 예금주, 연락처 | **양방향**: AES-256-GCM, KMS 보호 키링 | 고시 제7조(계좌번호 암호화)를 충족한다. 지급하고 화면에 보여 줘야 한다. |
| 스태프 TOTP 비밀 | **양방향**: 같은 키링 | 서버가 코드를 다시 계산해야 하므로 해시로는 둘 수 없다. |

## 패스키 (`passkey.rs`)

로그인 화면에서 이메일을 입력한 뒤 비밀번호 대신 "패스키로 로그인"을 누르면 기기의 지문·얼굴·화면 잠금으로 들어온다. 표준은 WebAuthn(FIDO2)이다.

- **저장:** 서버는 공개키만 저장한다(`identity.passkeys`). 비밀키는 기기를 떠나지 않으므로 DB가 유출돼도 로그인에 쓸 수 없다. 공개키는 비밀이 아니어서 암호화하지 않는다.
- **피싱 방지:** 브라우저가 서명 대상에 접속 주소(origin)를 넣는다. 서버는 우리 주소(스튜디오·관리자)만 받으므로 가짜 사이트에서는 동작하지 않는다.
- **2단계 인증 겸함:** 사용자 확인(지문·PIN, `userVerification: required`)을 요구한다. 패스키 로그인은 그 자체로 다중 인증(기기 소유 + 생체/PIN)이며 NIST AAL2·고시 제6조의 안전한 인증수단에 해당한다. 그래서 스태프는 패스키로 들어오면 인증 앱 코드를 따로 입력하지 않는다.
- **challenge:** 요청마다 한 번만 쓰고, 5분 동안 유효하며, 해시로만 저장한다.
- **복제 탐지:** 서명 카운터가 앞으로 가지 않으면 거절한다. 동기화 패스키는 카운터가 계속 0이라 이 검사에서 제외된다.
- **계정 노출 방지:** 로그인 옵션에 계정 정보를 넣지 않는다(discoverable credential). 그래서 이메일이 가입돼 있는지 드러나지 않는다. 먼저 입력한 이메일은 서명한 패스키의 계정과 같아야 한다.
- **등록:** 스튜디오 계정 정보 > 로그인에서 한다. 지금 비밀번호를 다시 확인한다(세션을 훔쳐도 자기 패스키를 심을 수 없게). 한 계정에 10개까지 둘 수 있다. 추가·삭제·로그인 실패는 감사 로그에 남는다.
- **알고리즘:** ES256, EdDSA, RS256. 서명 검증은 TLS용으로 이미 빌드한 aws-lc-rs로 한다. 1회 검증은 수십 μs다.
- **RP ID (`PASSKEY_RP_ID`):** 패스키는 도메인에 묶인다. 스튜디오(studio.audeniq.com)와 관리자(admin.audeniq.com)에서 한 패스키를 쓰려면 공통 상위 도메인 `audeniq.com`을 지정한다. 비우면 스튜디오 주소에서만 동작한다. **한 번 정하면 바꾸지 않는다.** 바꾸면 등록한 패스키를 모두 다시 등록해야 한다.
- **비밀번호 유지:** 비밀번호 로그인과 비밀번호 찾기는 그대로 둔다. 패스키를 잃어버렸을 때의 복구 수단이다.

## 비밀번호 규칙 (`password_policy.rs`)

비밀번호를 새로 정할 때(가입, 변경, 재설정) 적용한다. 이미 쓰고 있는 비밀번호는 다음 변경 때 적용된다.

- **길이:** 12~128바이트.
- **조합 규칙 없음:** 대·소문자·숫자·기호를 강제하지 않는다. NIST는 이런 규칙을 권하지 않는다.
- **거절하는 비밀번호:** NIST의 "흔하거나 추측 가능한 값 차단(SHALL)"과 고시 제5조의 비밀번호 작성 규칙에 따른다.
  - 흔한 단어 뒤에 숫자·기호만 붙인 것 (`password2024!`)
  - 키보드나 순서 패턴 (`1q2w3e4r…`, `qwerty…`, `0123…`)
  - 짧은 묶음의 반복, 서로 다른 글자가 5개 미만인 것
  - 이메일 아이디가 들어간 것
- **유출 비밀번호 대조:** 유출 목록 API(HIBP)는 외부 호출이 필요해서 쓰지 않는다.
- **부하:** 짧은 문자열을 비교할 뿐이라 거의 없다.
- **실패 횟수 제한(고시 제5조):** 계정·IP별 요청 제한으로 한다(15분 창).

## 스태프(개인정보취급자) 접속

관리 화면은 인터넷에서 접속하는 개인정보처리시스템이다.

- **2단계 인증 (`staff_mfa.rs`):** 고시 제6조(외부 접속 시 안전한 인증수단), FTC Safeguards Rule(MFA), NIST AAL2에 따른다.
  - 비밀번호에 더해 TOTP(RFC 6238, 30초, 6자리)를 요구한다. 대부분의 인증 앱에서 쓸 수 있다.
  - 처음 로그인하면 관리 화면이 설정 키를 보여 주고, 첫 코드를 확인하면 등록이 끝난다.
  - 한 번 쓴 코드는 다시 받지 않는다. 앞뒤 30초까지 허용하고, 코드 확인은 15분에 5번까지다.
  - `STAFF_MFA_REQUIRED=true`일 때만 켜진다(기본값 꺼짐). 개발 중에는 선택이고, **실제 운영(개인정보 처리) 시작 전에는 켜야 한다**(고시 제6조).
  - 인증 앱을 잃어버리면 owner가 `audeniq-admin --operator NAME staff reset-mfa EMAIL`을 실행한다. 그 계정의 세션이 모두 끊기고, 다음 로그인 때 다시 등록한다.
- **유휴 시간 만료:** 고시 제6조(일정 시간 업무가 없으면 접속 차단), NIST AAL2(30분)에 따른다.
  - 스태프 세션은 30분 동안 요청이 없으면 끊는다.
  - 마지막 사용 시각은 1분에 한 번만 기록해 쓰기 부하를 줄인다.
  - 절대 만료(12시간)는 기존대로다.
- **감사 기록:** 등록, 확인, 실패, 초기화를 감사 로그에 남긴다. 스태프 접근 기록 2년 보관(고시 제8조)은 기존대로다.

## 적용하지 않은 것과 이유

- **일반 회원(아티스트) 2단계 인증:** 회원은 정보주체이고 개인정보취급자가 아니어서 법적 요구가 없다. 필요하면 같은 TOTP 모듈로 선택 기능을 붙일 수 있다.
- **비밀번호 pepper:** 해시에 서버 비밀을 섞는 것은 NIST의 SHOULD다. 키를 회전할 때 모든 사용자가 비밀번호를 재설정해야 하는 운영 위험이 있어 적용하지 않았다. Argon2id만으로도 DB 유출 대비 기준은 충족한다.
- **주민등록번호 등 고유식별정보:** 수집하지 않는다. 본인인증은 연계정보(CI) 해시만 둔다.
