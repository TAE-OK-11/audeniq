# AUDENIQ 기술 결정 상세 리뷰

- 대상: `docs/BLUEPRINT.md` FINAL 1.0 (23장, 1305줄) + F1 구현 코드 대조
- 관점: 각 기술 결정이 (a) 요구사항에 맞는가, (b) 대안 대비 합리적인가, (c) 리스크가 문서화되어 있는가
- 판정: 잘됨 13 / 수용 3 / 의문 1. 치명적 오판 없음.

---

## 1. 언어: Rust (Axum / Tokio / SQLx) — 잘됨 (조건부)

**결정:** 백엔드 전체를 Rust 모듈러 모놀리스로. Python 런타임 의존성 금지.

**평가:** 권리·정산처럼 "틀리면 돈이 나가는" 도메인에는 합리적. 소유권·타입 시스템이 상태 전이 실수, 금액 계산 실수(i128 고정소수점 강제)를 컴파일 타임에 잡는다. SQLx의 쿼리 검증도 한몫. F1에서 28개 테스트 통과로 결정이 이미 검증됨.

**리스크:** 1인 팀 기준 학습 곡선은 이미 넘었음(본인이 Pingola도 Rust). 진짜 리스크는 팀 확장 시점의 채용 풀이 좁다는 것. 지금은 문제없고, 그때 가서 판단할 문제.
**대안 비교:** Go(생산성↑·안전성↓), TypeScript(생태계↑·런타임 리스크↑). 도메인 특성상 Rust가 정답에 가까움.

## 2. 엣지: Rust/WASM Cloudflare Workers BFF — 의문 (유일하게 논쟁적)

**결정:** 사용자 요청 BFF를 Rust/WASM(workers-rs)으로 구현.

**평가:** BFF는 얇은 프록시·인증 계층이라 Rust의 강점(소유권, 제로코스트 추상화)이 거의 발휘되지 않는다. workers-rs는 커뮤니티가 작고 디버깅·배포·콜드스타트 실측 자료가 TypeScript 대비 부족하다. "단일 언어" 명분은 있으나 BFF와 코어 API는 어차피 HTTP 경계라 언어 통일의 실익이 작다.

**제안:** 이미 구현됐고 빌드 통과했으니 되돌릴 필요 없음. 단, BFF에 복잡한 로직을 넣지 말고(얇게 유지), 문제 생기면 TypeScript로 교체하는 것을 옵션으로 열어둘 것.

## 3. DB: PostgreSQL 17 단일 — 잘됨 (강력 유지 권장)

**결정:** 큐·outbox·감사·세션·레이트리밋까지 전부 PostgreSQL. Redis/Kafka 없음. L13(상태 전이+job+outbox 단일 트랜잭션)이 핵심 요구사항.

**평가:** 이 결정이 전체 아키텍처의 백본. 분산 트랜잭션 없이 원자성을 얻는 유일하게 단순한 방법. `SKIP LOCKED` 큐는 이 규모에서 충분하고, Redis를 넣는 순간 dual-write 문제가 생긴다. 세션·레이트리밋까지 PG에 넣은 것도 운영 단순성 우선으로 맞음.

**리스크/제안:**
- `jobs`/`outbox`/`audit_events`는 append-only라 테이블 bloat가 필연. **보존·아카이브·파티셔닝 정책이 문서에 없음** → F2 전에 추가 권장.
- 레이트리밋 global 버킷(`login:global`)은 공격 시 단일 행에 쓰기가 직렬화됨. 의도된 감속이라 허용 가능하나, 규모가 커지면 인메모리 윈도우 병행.

## 4. 스토리지: R2 직접 업로드 — 잘됨

**결정:** 브라우저→R2 직접 업로드. presigned URL은 키·MIME·크기·nonce·기한에 바인딩. 완료 후 서버가 HEAD 검증 → 불변 키로 조건부 복사. ETag를 SHA-256으로 취급 금지 명시(§3.1).

**평가:** 실무 수준의 보안 계약. API 서버로 파일을 중계하지 않는 것이 핵심(대역폭·메모리 이중 부과 방지). R2 egress 0원은 음원 유통의 비용 구조에 최적. S3 호환이라 이전도 쉬움. multipart 미완료 abort(24h) 정책까지 문서화됨.

## 5. 네트워크: Workers VPC Service + Tunnel — 수용 (리스크 문서화됨)

**결정:** 주경로 VPC Service + Tunnel. 평상시 대체 경로 OFF, 수동 2인 승인 전환 런북(§9.5).

**평가:** 문서 스스로 "베타 기준"임을 인정(§12.1, §23.1)하고, fallback 절차가 7단계로 구체적이라 관리 가능. "동일 호스트 cloudflared 2개는 호스트 장애를 못 막는다"는 잔여 위험까지 명시한 정직함이 좋음.

**대안:** Tailscale/WireGuard 자체 터널 — BuFi Tunnel 경험이 있어 나중에 교체할 카드가 있음. 지금 바꿀 필요는 없고, VPC GA/요금제 재평가는 GO 게이트에 이미 포함됨.

## 6. UI: React + TS + Vite, 관리자 분리 — 잘됨

**결정:** 업무용 React+TS+Vite, 관리자 별도 앱. 기존 랜딩·Studio·설문 자산은 byte-for-byte 보존.

**평가:** 표준 스택. 기존 자산을 손대지 않은 건 현명함(디자인 부채를 안 짊어짐). 관리자 앱 분리는 보안상 정석(별도 Access 정책+MFA).

## 7. 아키텍처: 모듈러 모놀리스, gRPC 초기 금지 — 잘됨

**결정:** `audeniq-api`+`audeniq-worker` 2 바이너리 유지. "단계는 논리적으로, 실행은 가볍게"(§14.3). DSP 어댑터를 마이크로서비스로 안 나눔. gRPC는 물리 서버 분리 시에만.

**평가:** 정석. DSP 어댑터는 I/O 바운드라 분리 이득이 없음. CPU 바운드인 오디오 QC만 호스트 분리 예외로 둔 판단이 정확함.

## 8. 데이터 모델: 6 스키마·불변 계층·4축 상태 — 잘됨 (야심적이나 정합)

**결정:** identity/catalog/rights/distribution/finance/operations 6 스키마. draft→revision→snapshot→package 불변 계층. 4개 직교 상태축(§2.4, 전이표는 거부 기본값). 테넌시는 `org_id`+ACTIVE membership+`resource_acl` 삼중 검사. `party ≠ payee` 분리. `ON DELETE RESTRICT` 우선.

**평가:** 도메인 이해도가 높음. 불변 trigger, `STALE` 핀, INV-01~15 테스트 식별자까지 정의한 건 실무급. F1에서 rights/finance를 예약 스키마로 두고 26 테이블만 만든 스코핑도 잘함.

**제안:** §8과 연결 — 보존·아카이브 정책 없음. 불변 테이블이 무한 증가하는 구조라 파티셔닝 계획 필요.

## 9. 보안 설계 — 잘됨

**결정:** Argon2id, 토큰 해시 저장, HttpOnly/SameSite/Secure 쿠키, Origin+Fetch-Metadata, DB 레이트리밋, `grants.sql` 역할 분리, append-only 감사.

**평가:** F1 코드에서 실제 강제됨을 리뷰로 확인. 특히 "2인 승인이지만 승인자 2명이 없으면 그 행위를 보류" 같은 현실적 단서가 좋음. 브라우저 제공 사용자 ID 헤더를 신뢰하지 않는 원칙도 코드에 반영됨.

## 10. 공개 콘텐츠 D1 복제본 — 잘됨

**결정:** `publication_revisions` 원본은 PG. 게시 승인+outbox를 동일 트랜잭션에 기록 → Worker가 D1에 멱등 upsert. D1에서 권리·정산 원장 작성 금지.

**평가:** 경계가 명확. CMS 과잉 개발을 명시적으로 금지한 것도 좋음.

## 11. 백업: pgBackRest + WAL — 잘됨 (미검증 명시)

**결정:** 주간 full + 일간 incremental + 상시 WAL archive. RPO≤1h / RTO≤4h 목표. 복원 드릴 월 1회. R2는 별도 버전관리·복제.

**평가:** "목표 위반 시 달성된 것으로 광고하지 않는다"는 문구가 핵심. 복원 직후 LEASED/`SENT_UNKNOWN` 재실행 금지 규칙까지 있는 게 실무적.

**빠진 것:** R2 버전관리·DB 백업 스토리지의 월 비용 추정이 없음(→ 제안 3).

## 12. 관측 — 수용 (최소한)

**결정:** OTel 풀스택 미채택. §9.2에 보수적 임시 임계값(`MemAvailable`<300MiB 등)을 실제 모니터링에 등록.

**평가:** 미채택 결정 자체는 맞음. 다만 JSON 구조화 로깅은 이미 있으니 최소 `/metrics` 엔드포인트 정도는 P1 전에 권장.

## 13. DDEX: ERN 4.3.2 중심, MockDSP 우선 — 잘됨

**결정:** ERN 4.3.2 + 프로파일 2.3.1 중심 설계. 단, 상대방 수신 버전은 개별 계약으로 확정. Implementation Licence를 별도 확인 항목으로 분리. 첫 구현은 MockDSP(ACCEPT/REJECT/TIMEOUT/UNKNOWN/중복/지연 재현) + contract-test suite로 DSP 확장.

**평가:** "스키마 통과 ≠ 접수" 명시, 가상 ACK 금지, `SENT_UNKNOWN` 자동 재전송 금지 — 실무에서 터지는 함정을 문서로 미리 막음. DSP-01~12 테스트 시나리오가 구체적.

## 14. 정산: 이중기입 원장, 수동 지급 우선 — 잘됨

**결정:** Σdebit=Σcredit 강제, 수정 대신 역거래·조정거래. 통화 분리 합산 금지. `MATCH_REVIEW`에서 자동 전기 금지. 초기 송금은 관리자 승인 후 수동 지급. 은행 자동지급 OFF.

**평가:** 돈 다루는 시스템의 정석. 세금/원천징수를 전문가 검토 범위로 둔 것도 범위 인식이 정확함.

## 15. 실행 E-0~E-5 — 잘됨

**결정:** 전송≠접수≠라이브 상태 분리. attempts/ack append-only. 외부 송출은 시도 ID+idempotency key로 상관관계 연결(DSP 멱등 미가정). 보상은 UPDATE가 아닌 cancel/replace/takedown 작업으로.

**평가:** 분산 시스템의 정석 패턴. E-1 FreshnessGuard(송출 직전 권리·계약·hold 재확인)가 핵심 안전장치.

## 16. 서버: Debian 13, Compose, 2/4→4/8/160 — 잘됨

**결정:** 단일 호스트 시작. LAB(2/4)은 개발·부하 측정 전용, 실발매 금지. PROD-A(4/8/160) 또는 코어·QC 분리형. Kubernetes 미채택.

**평가:** 규모에 맞는 판단. QC 분리 트리거(§1.3.6)를 수치 기준으로 정의한 점이 좋음.

## 17. 계획 F0~F9 / P0a~P6 — 잘됨 (야심 vs 현실 균형)

**결정:** F0 설계동결 → F1 파운데이션 → F2 pre-submit/Stage1 → ... → F9 DSP 확장. 선행 관계 명시(ERN 코드는 synthetic fixture로 선행 개발 가능, F6은 파트너 속도에 종속).

**평가:** 핵심은 §23.1의 3분리 — **개발 착수 GO / 첫 송출 GO / 운영 GO**를 별개로 추적. "기능 완료 ≠ 상업 승인"을 구조화한 게 이 계획의 가장 강한 부분. 미확정 7항(DSP 계약, Merlin/LIMBO, ISRC 발급, 미성년 동의 법률 검토, 외부 OCR, 은행 자동지급, VPC 베타) 전부 기본 OFF+게이트로 잠금.

## 제안 3가지

1. **`jobs`/`outbox`/`audit_events` 보존·아카이브·파티셔닝 정책**을 F2 전에 문서에 추가 (PG 단일화의 대가인 bloat 관리).
2. **BFF는 얇게 유지.** 복잡해지면 TypeScript 교체 옵션을 열어둘 것 (유일한 논쟁적 결정).
3. **비용 모델을 §11에 추가.** R2(저장·작업 요금)/Workers(유료 플랜)/백업 스토리지 월 추정. egress 0원이 전부가 아님.
